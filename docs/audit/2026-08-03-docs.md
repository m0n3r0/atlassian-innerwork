## High severity

### H1. `docs/migration-guide.md` — the documented CLI surface does not exist

The migration guide is written against a CLI that was renamed before Phase 10
landed. The actual subcommands are `export` / `import` / `migrate` / `metrics`
with `--database-url` (or `INNERWORK_DATABASE_URL`) and a positional `input`
argument — there is no `export-domain`, no `import-domain`, no `--db`, no
`--indent`, no `--input`, no `--principal`, and no `upgrade` subcommand.
Verified with `uv run innerwork --help` and `uv run innerwork export-domain`
(argparse: `invalid choice`).

Affected claims (doc text → actual behavior):

| Doc claim | Actual behavior |
|---|---|
| §1 "Document what `innerwork export-domain` and `innerwork import-domain` actually do." | No such subcommands. `innerwork export` / `innerwork import` are the wrappers. |
| §2.1 ``innerwork export-domain --db <path/to/domain.db> [--indent N]`` | `innerwork export [--database-url sqlite:///...] [--out FILE]`. No `--db`, no `--indent`. `--out` writes to a file; otherwise JSON goes to stdout with `indent=2` hard-coded (`cli.py` → `export_domain_json(store, indent=2)`). |
| §2.2 ``innerwork import-domain --db <path/to/fresh.db> --input <export.json>`` | `innerwork import [--database-url sqlite:///...] <input>` — input is a positional argument, not `--input`. |
| §2.3 ``innerwork migrate --source synthetic --db <path/to/fresh.db>`` | `innerwork migrate --source synthetic --database-url sqlite:///...`. |
| §2.4 ``innerwork metrics --db <path/to/domain.db> [--principal <name>]`` | `innerwork metrics --database-url sqlite:///...`. No `--principal` flag exists; the rollup always runs without a principal (accurate in `docs/metrics-dashboard.md` §3, contradicted here). |
| §3 round-trip procedure (4 lines, all using `export-domain`/`import-domain`/`--db`) | Same rename applies. The procedure's *semantics* (fresh target, byte-identical diff) are real — verified live — but every command line as printed fails. |
| §5 failure table ("Operator pointed `--db` at a populated database") | The flag is `--database-url`. |
| §7 "Schema upgrades happen through `innerwork upgrade`" | No `upgrade` subcommand exists (see `cli.py` command list). |

Suggested fix: rewrite §1, §2, §3, §5, §7 to use `export` / `import` /
`--database-url` / positional `input`, or (better) regenerate the CLI
examples straight from `--help` output. §4 (markdown importer) is accurate
and needs no changes (see P4 below).

### H2. `docs/metrics-dashboard.md` — wrong flag, and two false negative claims

1. **Wrong flag.** §1, §4 (Patterns A/B/C), and §6 all use
   ``innerwork metrics --db path/to/store.sqlite3``. The flag is
   `--database-url` (verified `uv run innerwork metrics --help`).
2. **False: "No request-level telemetry."** §2 states: "**No request-level
   telemetry.** `innerwork` does not record HTTP request counts, latencies,
   error rates, or any user-agent data." The Phase-8 observability middleware
   in `src/innerwork/app.py` (lines 121–158) records `http_requests_total`,
   `http_request_errors_total`, and `http_request_duration_ms` on every
   request, and `src/innerwork/observability.py` declares those metrics plus
   `domain_writes_total`, `domain_write_conflicts_total`, `span_duration_ms`.
3. **False: "no metrics endpoint."** §4 states "`innerwork` deliberately does
   not run a metrics endpoint." The FastAPI app exposes `GET /metrics`
   serving Prometheus 0.0.4 text (`app.py:172–182`), and
   `docs/operations-runbook.md` documents it. `CHANGELOG.md` also claims no
   metrics endpoint exists (see H3) — the runbook is the doc that is right.

Suggested fix: clarify that §2's telemetry-negative claim is scoped to the
*analytics rollup* (the rollup indeed carries no request telemetry), change
"does not run a metrics endpoint" to "the analytics rollup is not served as
an endpoint; the Phase-8 `GET /metrics` Prometheus surface is separate and
unchanged", and swap `--db` → `--database-url` throughout.

### H3. `CHANGELOG.md` [Unreleased] — "no metrics endpoint exposed by the FastAPI app" is false

Under `[Unreleased] → Added — Phase 10 → Not changed`:

> - No telemetry, no metrics endpoint exposed by the FastAPI app; the
>   analytics rollup is read on-demand via `innerwork metrics`.

The FastAPI app *does* expose a metrics endpoint: `GET /metrics` renders the
in-process Prometheus registry (`src/innerwork/app.py:172–182`, added in
Phase 8). This sentence also contradicts the repo's own
`docs/operations-runbook.md` ("The `/metrics` endpoint serves Prometheus text
format on the same port as the API"). The intended meaning was likely
"Phase 10 adds no new telemetry / no new metrics endpoint", but as written it
is a false absolute claim and violates the project's anti-hallucination
posture.

Suggested fix: reword to "No telemetry is *added* in Phase 10; the Phase-8
`GET /metrics` Prometheus endpoint is unchanged, and the analytics rollup is
additionally exposed on-demand via `innerwork metrics`."
