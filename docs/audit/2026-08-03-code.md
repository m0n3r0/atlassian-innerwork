## MEDIUM

### M1. Portability export/import silently drops `visibility`/`members` from projects and spaces

- File: `src/innerwork/portability.py:92-95` (projects SELECT), `:128-133`
  (spaces SELECT), `:247-248` and `:275-276` (INSERT column lists)
- The `projects` and `spaces` tables carry Phase 6 permission columns
  (`domain_store.py:1045-1046`, `:1103-1104`), but `export_domain` selects
  only the 5 pre-Phase-6 columns and `import_domain` inserts only those.
  Import therefore falls back to the table defaults (`'internal'`, `'[]'`).
- Verified: a `public` project with `members=("alice","eng")` and a
  `restricted` space with `members=("bob",)` both round-trip to
  `visibility='internal'`, `members=()`.
- Impact: any store with non-default visibility silently loses its
  permission state on export/import. `restricted` widens to `internal`
  (access broadens), `public` narrows to `internal`, member lists vanish.
  The byte-identical round-trip test (`tests/test_portability.py:191`)
  passes only because its seed uses defaults everywhere.
- Fix: add `visibility, members` to the projects/spaces SELECT and INSERT
  statements (export `members` as the decoded tuple), and extend the
  round-trip test to seed a non-default visibility.

### M2. Mixed-case mention handles never resolve — silent notification loss

- File: `src/innerwork/notify.py:110` (validation), `:133-139` (register),
  `:144-160` (lookup)
- `User.__post_init__` accepts any-case handles (`_MENTION_RE` is
  case-sensitive on `[A-Za-z0-9]`), and `UserDirectory.register` stores the
  handle verbatim as the dict key. But `parse_mentions` lowercases every
  handle (`notify.py:63`) and `resolve_handles`/`get_by_handle` look up
  `handle.lower()`. A user registered as `Alice` is therefore unreachable
  by any mention — `@alice` and `@Alice` both miss.
- Verified: `UserDirectory([User(handle="Alice")])` resolves neither
  `@alice` nor `@Alice`.
- Fix: normalize handles to lowercase at registration (or reject
  non-lowercase handles in `User.__post_init__`) so the invariant
  "directory keys are lowercase" holds.

### M3. `docs/migration-guide.md` documents CLI commands that do not exist

- File: `docs/migration-guide.md:76-92` (§2.1/§2.2)
- The guide shows `innerwork export-domain` / `innerwork import-domain`
  with a `--db <path>` flag. The shipped CLI defines `export` / `import`
  subcommands with a `--database-url` flag (`src/innerwork/cli.py:114-134`,
  `:273-285`). An operator following the guide gets an argparse error.
- Fix: update the guide's examples to `innerwork export --database-url
  sqlite:///path.db --out snapshot.json` and `innerwork import
  --database-url sqlite:///fresh.db snapshot.json`, or add
  `export-domain`/`import-domain` aliases.

## LOW

### L1. UNIQUE-violation handler mislabels any unique constraint as key reuse

- File: `src/innerwork/domain_store.py:244-247` and `:531-534`
- `create_project`/`create_space` map `"projects.key" in str(exc) or
  "UNIQUE" in str(exc).upper()` to `DuplicateProjectKeyError` /
  `DuplicateSpaceKeyError`. A duplicate `project_id`/`space_id` (PRIMARY
  KEY) insert also contains "UNIQUE" in SQLite's message, so it is
  misreported as "project key already exists: ...". Misleading diagnostics
  for API clients.
- Fix: match on the specific constraint name (e.g.
  `"projects.key"`/`"spaces.key"`) before falling back to the generic
  UNIQUE branch.

### L2. `truncated` flag in AI-context budget loop is sticky

- File: `src/innerwork/ai_context.py:532-534`
- When the first over-budget candidate is skipped, `truncated=True` is set
  and never cleared, even when a later, smaller candidate fits the budget
  and is included. The flag therefore reports "truncated" for bundles that
  actually admitted every candidate that fit (priority order is preserved,
  so the greedy skip is otherwise correct).
- Fix: only set `truncated` when a candidate is skipped AND no later
  candidate is admitted, or track it as "any candidate skipped".

### L3. Synthetic fixture uses int ids for TEXT-primary-key tables

- File: `src/innerwork/migrators/synthetic_fixture.py:181,191,199,208`
  (`"link_id": 1`, `"comment_id": 1`, ...)
- `work_item_page_links.link_id`, `work_item_comments.comment_id`, and
  `page_comments.comment_id` are `TEXT PRIMARY KEY` columns
  (`domain_store.py:1139,1166,1182`). The fixture inserts integers, which
  SQLite coerces to text via column affinity — the import works, but a
  re-export emits `"1"` (string), so the fixture payload is not
  byte-stable under export→import→export the way real (string-id) stores
  are, contradicting the portability contract's byte-identical claim.
- Fix: use string ids (`"link-001"`, `"comment-001"`) in the fixture and
  regenerate `tests/fixtures/synthetic_migration.json`.

### L4. Stale docstring: search claims permissions are a later phase

- File: `src/innerwork/search.py:13-15`
- The module docstring says "Permissions and redaction live in Phase D;
  this slice returns every matching entity", but the code filters by
  `principal` (lines 256-292, added Phase 6). The docstring misleads
  future readers about the permission posture of the search surface.
- Fix: update the docstring to describe the principal-gated filtering.

### L5. Broker idempotency: validation-failure path does not bind the idempotency key

- File: `src/innerwork/broker.py:47-50`
- When `spec.canonicalized()` raises (line 49), `_record_failure` is
  returned without saving an idempotency record — unlike the
  enforcement-failure path (lines 73-75), which binds the key to the
  failure operation. A client retrying a permanently invalid payload with
  the same key gets a fresh failure operation id every time, instead of a
  stable replay.
- Fix: save the idempotency record (with the failure operation id) in the
  validation-failure branch too.

### L6. `x-request-id` header missing on exception-path responses

- File: `src/innerwork/app.py:132-142`
- The observability middleware sets `response.headers["x-request-id"]`
  only on the success path. When `call_next` raises, the generated 500
  response carries no request id, making error-path log correlation
  (request id → stack trace) harder than the success path.
- Fix: set the header on the exception path as well, or use an
  exception handler that echoes the bound request id.

### L7. Markdown importer does not ISO-validate the import-wide `created_at`

- File: `src/innerwork/markdown_importer.py:118-119, 386`
- `scan_markdown_tree`/`import_markdown_tree` accept a `created_at`
  argument and pass it straight to `create_space`/`create_page` as the
  persisted timestamp; only *frontmatter* `created_at` gets ISO-8601
  validation (lines 271-285). A malformed programmatic `created_at` would
  be persisted verbatim. The CLI does not expose the flag today, so
  exposure is limited to library callers.
- Fix: run `_validate_iso_timestamp` on the import-wide `created_at`.
