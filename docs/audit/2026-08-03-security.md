# Security & Trust Audit — 2026-08-03

**Scope:** everything built in phases 0–10 through today, on `main` @ `328561d`.
**Auditor:** atlassiansec (kanban task `t_023cd590`).
**Method:** source review + runtime verification (experiments) + full test suite (332 passed) + history scan + dependency check.

**Severity scale:** `HIGH` / `MED` / `LOW`. No `HIGH` findings: every attack surface is
local, single-tenant, and operator-triggered (CLI or trusted-host HTTP); there is no
remote-unauthenticated path into the store. `MED` items are gaps that defeat a *documented
control* (audit logging, input caps); `LOW` items are hygiene, robustness, or doc-drift.

## 1. Threat-model conformance (`docs/threat-model.md` vs code)

**Bottom line: the documented trust boundaries are real and mostly accurate. Two controls
are effectively inert in the shipped tooling, and one enforcement inconsistency exists.**

### F1 — MED — Audit sink is never wired by any shipped surface (CLI or serve)

The audit log is the core phase-7 repudiation control. `DomainStore.audit_sink` defaults to
`None` (`src/innerwork/domain_store.py:110`) and `_audit` no-ops when unset
(`domain_store.py:133-134`). Nothing in the shipped tooling ever sets it:

- CLI: `_domain_dispatch` constructs `DomainStore(_resolve_database_url(args))`
  (`src/innerwork/cli.py:289`) — no sink, no `--audit-log` flag, no env var.
- Server: `AppState.__init__` constructs `DomainStore(domain_db_path)`
  (`src/innerwork/app.py:98`) — no sink.
- `scripts/backup.py`, `scripts/restore.py`, `scripts/rollback_drill.py` — no sink.

Runtime-verified: a store built exactly as the CLI builds it emits **zero** audit rows for
`project-create`, `work-item-create`, `work-item-transition`, `export`, or comment writes;
no `audit.db` is ever created. The threat model §6.1 lists wiring as an *operator
responsibility*, but the shipped operator interface (CLI) provides **no mechanism** to
perform that wiring without writing custom Python. An operator following the documented
path gets silently no audit logging.

*Suggested fix:* add `--audit-log <path>` to the CLI and an `INNERWORK_AUDIT_DB` env var;
wire `SqliteAuditSink` in `_domain_dispatch` and `AppState` when set. Update
`docs/threat-model.md` §6.1 to point at the mechanism.

### F2 — LOW — `actor_kind` is hardcoded `"system"`; spoofing mitigation is not wireable

`DomainStore._audit` always stamps `actor_kind=self.audit_actor_kind`
(`domain_store.py:139`), a store-level attribute defaulting to `"system"`
(`domain_store.py:111`). There is no per-call `actor_kind` parameter anywhere in the store
API. Runtime-verified: a transition performed by `bob` is recorded as `actor_kind=system`.
The threat model marks spoofing mitigation as "partial (operator wires upstream identity)",
but an operator **cannot** wire per-call identity without modifying the store. `Notifier`
hardcodes `"system"` the same way (`src/innerwork/notify.py:463`).

*Suggested fix:* accept `actor_kind` per call in `_audit` (default `"system"`), and have
`transition_work_item` / `create_page` / `update_page` / `Notifier.dispatch` forward the
caller's kind. Keep the enum closed.

### F3 — LOW — several mutation surfaces are un-audited even with a wired sink (by design, undocumented)

Runtime-verified with a wired sink: only `confluence_page` (page create) and `jira_workflow`
(transition) events are emitted. Project creation, work-item creation, space creation,
comment creation, link create/delete, and `import-markdown` bulk import emit nothing —
`AUDIT_SURFACES` is a closed enum (`src/innerwork/audit.py:53-62`) that excludes them.
This is a deliberate scoping decision (documented in `audit.py`'s docstring) but the threat
model's repudiation row lists only the *included* surfaces, so a reader cannot tell what is
excluded. Also: `import-markdown` (PR #22) has no dedicated surface — a bulk import appears
only as per-page `confluence_page` creates.

*Suggested fix:* either extend `AUDIT_SURFACES` with `work_item`/`comment`/`link`/
`markdown_import` (and emit from the store mutations), or explicitly enumerate the
excluded surfaces in `docs/threat-model.md` §4/§5.

### F4 — LOW — read-gate inconsistency: direct read endpoints bypass `can_read`

`permissions.py` documents `can_read` as the single read-gate and says "Higher layers MUST
funnel reads through this function" (`src/innerwork/permissions.py:18-20`). It is enforced
on `/v1/search`, `/v1/ai_context`, and `/v1/analytics/*` only
(`src/innerwork/domain_api.py:828-962`). The direct read endpoints — `GET /v1/projects`,
`/v1/work_items`, `/v1/spaces`, `/v1/pages`, `/v1/*/comments`, `/v1/links` — never parse
`X-Innerwork-Principal` and return full content regardless of `visibility`/`members`. A
`restricted` space's pages are filtered out of `/v1/search` for an anonymous caller but fully
readable via `GET /v1/spaces/{id}/pages`.

Given the documented single-tenant / trusted-host posture this is LOW, but it is a real
conformance gap: the visibility model is not enforced at the graph's direct read surface.
*Suggested fix:* apply `parse_principal_header` + `can_read` on direct read endpoints (or
document the direct surface as operator-only and enforce the header on all `/v1` reads).

### F5 — LOW — doc drift

- `src/innerwork/field_acl.py:13,45` cites "docs/threat-model.md §3.4" — the live
  `docs/threat-model.md` has no §3.4 subsection (its sections are unnumbered under §3).
- `src/innerwork/audit.py:16-17` says "`JsonlAuditSink` is the export surface for backups"
  and the module docstring says it is "used by `scripts/backup.py`" — `scripts/backup.py`
  uses `sqlite3.Connection.backup()`, never `JsonlAuditSink`.
- `docs/threat-model.md` §1 scope does not list the markdown importer (PR #22) or the
  `import-markdown` CLI surface, both added after the model was written.
- `docs/archive/threat-model.md` exists alongside the live model; the archive copy is not in
  the anti-hallucination ALLOWLIST (it currently trips nothing, so this is latent).

*Suggested fix:* correct the two stale references; add the import surfaces to the threat
model scope; either delete `docs/archive/threat-model.md` or allowlist it intentionally.

## 5. Input safety

### Markdown importer (PR #22, `src/innerwork/markdown_importer.py`)

**Path traversal — not applicable / clean.** The importer is read-only with respect to the
filesystem: it derives space keys (sanitized through `validate_space_key`,
`markdown_importer.py:288-306`) and titles from paths, and writes only to the store. No
filename-derived filesystem writes exist, so traversal cannot occur.

**Symlink escapes — blocked (verified).** Space directories that are symlinks are skipped
(`markdown_importer.py:127`); every file entry is checked with `is_symlink()` and skipped
(`markdown_importer.py:207-208`). Runtime-verified: a symlink inside a space pointing
outside the import root (including `/etc/hostname`) imports zero pages.

**Malformed frontmatter — handled cleanly.** Unclosed `---` blocks, non-mapping YAML,
non-string/blank titles and authors, over-length titles, and invalid `created_at` all raise
`MarkdownImportError` with the file named (`markdown_importer.py:309-343, 218-268`).

**YAML alias "billion-laughs" — verified not exploitable.** `yaml.safe_load` composes
aliases as shared references rather than expanding copies; a depth-6 multiplicative alias
chain parsed in 0.00s. This is a clean axis.

**Zip-bomb / archive handling — N/A.** The importer accepts a directory tree of plain `.md`
files; no archive format is parsed. The large-file gap below (F8) is the relevant control.

### F8 — MED — no pre-read file-size cap; body limit enforced only after a full read

`_scan_pages` calls `path.read_text(encoding="utf-8")` (`markdown_importer.py:168`) *before*
the `_PAGE_BODY_MAX = 200_000` check (`markdown_importer.py:170-173`). Runtime-verified: a
40 MB `.md` file is read fully into memory (0.13 s) and only then rejected. A
multi-GB file — accidental or malicious — exhausts process memory before any cap is
applied. The frontmatter block is likewise unbounded before `yaml.safe_load`.

*Suggested fix:* check `path.stat().st_size` against a cap (e.g. 2–5 MB) before `read_text`;
cap the frontmatter block (e.g. 16 KB) before parsing. Both caps belong in
`scan_markdown_tree` so they also gate `--dry-run`.

### F9 — LOW — `UnicodeDecodeError` / `RecursionError` escape as tracebacks

A non-UTF-8 `.md` file raises `UnicodeDecodeError` (a `ValueError`, not
`MarkdownImportError`) at `markdown_importer.py:168`; a deeply nested YAML frontmatter
(3000 levels — runtime-verified) raises `RecursionError` inside `yaml.safe_load`. Neither is
caught by `scan_markdown_tree` nor by the CLI's `except (MarkdownImportError, OSError)`
(`cli.py:401`), so the import dies with a traceback and exit code 1 instead of a clean
per-file error and exit code 2. *Suggested fix:* catch `UnicodeDecodeError` and
`RecursionError` in `_scan_pages` and map to `MarkdownImportError`; optionally bound YAML
nesting depth.

### Portability JSON import (`src/innerwork/portability.py`)

**Schema validation — sound.** `format_version` / `schema_version` are checked against the
wire constants (`portability.py:346-356`); collections must be lists; the fresh-target check
runs before any insert (`portability.py:239-240`); the whole import is one transaction
(single `with store._connect()`, so a mid-import failure rolls back — sqlite3 connection
context-manager semantics). FK-safe insert ordering and sequence reseeding are correct.

### F10 — LOW — no input size limit; deep-nesting `RecursionError` not mapped

The CLI reads the entire input file (`cli.py:363`) and `json.loads` parses it fully —
there is no byte cap (a 600 KB / 200k-row envelope parsed fine; a multi-GB envelope would
not). Deeply nested JSON raises `RecursionError`, which is not a `DomainImportError`
(runtime-verified with a 2000-deep array) and not caught by the CLI's `except
DomainImportError` (`cli.py:369`), producing a traceback. A non-UTF-8 input likewise raises
`UnicodeDecodeError` uncaught. *Suggested fix:* cap input file size (e.g. 50 MB) in the CLI
and/or `import_domain_json`; wrap `json.loads` to map `RecursionError` (+ `ValueError`) to
`DomainImportError`.

## 6. Audit log integrity (`store.audit_sink`)

**Bottom line: the append-only mechanism is real, tested, and cannot be bypassed by the
application — but it is inert unless wired (F1).**

- **Append-only:** SQL triggers `audit_log_no_update` / `audit_log_no_delete` `RAISE(ABORT)`
  on UPDATE/DELETE (`src/innerwork/audit.py:191-200`); `SqliteAuditSink.record` performs
  INSERT only; `JsonlAuditSink` opens in append mode; the module exposes no UPDATE/DELETE
  API. Trigger rejection is covered by `tests/test_audit.py:77-101` (direct UPDATE and
  DELETE both raise `sqlite3.DatabaseError`).
- **CLI exposure:** the CLI exposes no audit read/export subcommand. Read events are
  deliberately not logged (documented in the threat model §4 and `audit.py` docstring).
  `export_jsonl` exists on `SqliteAuditSink` and is exercised by tests; `scripts/backup.py`
  preserves the audit DB via page-level SQLite backup.
- **Bypassability:** the only bypass is host-level — a DBA can `DROP TRIGGER` or edit the
  file out-of-band. This is explicitly documented as a soft guard, not a security boundary,
  in both `audit.py:9-14` and the threat model §5. No application code path can rewrite or
  delete audit rows. The *silent* bypass is F1: with the default (unwired) sink, mutations
  happen with zero audit trail and no warning.

## 7. Deployment posture note (informational, not a finding)

`innerwork serve` defaults to `127.0.0.1` (`cli.py:57`), but `--host 0.0.0.0` is accepted.
The `/v1` API has no authentication: mutations require only a 16–128 char idempotency
header, and the `X-Innerwork-Principal` identity is client-supplied with no verification
(`permissions.py:159-160`: "identity, not authorization proof"). This is consistent with the
documented trusted-host / single-tenant posture, but operators must not expose the server
beyond a trusted host.
